# Requirements Document

## Introduction

`bellud` is a new Go service (`services/bellud`) that becomes the single externally exposed server process on port 4096. It replaces `packages/cli serve` as the front door, spawns the existing TypeScript server as a loopback-only child, and reverse-proxies every route it does not yet own (including SSE and WebSocket). It embeds a vendored, renamed copy of the Toise graph engine, the Bellu Graph Engine, which collectors feed in-process. Route groups migrate from TypeScript to Go in stages, guarded by a route ownership table and contract tests against the `packages/protocol` schemas.

These requirements are derived from the approved design document (`design.md`).

## Glossary

- **Bellud**: The Go service in `services/bellud` that acts as the front door and hosts the Graph_Engine.
- **TS_Child**: The existing TypeScript server (`packages/cli` serve, using `packages/server`) run by Bellud as a loopback-only child process.
- **Supervisor**: The Bellud component (`internal/tschild`) that starts, watches, restarts and stops the TS_Child.
- **Router**: The Bellud component (`internal/server`) that resolves the owner of each request through the Route_Table and dispatches it.
- **Route_Table**: The embedded `routes.yaml` file listing every route with its method, pattern, group, owner, public flag and stream flag.
- **Owner**: The value `go` or `ts` assigned to a route in the Route_Table.
- **Protocol_Operation**: One operation (method and path) in the OpenAPI document generated from the TS `Api` in `packages/protocol`.
- **Authenticator**: The Bellud component (`internal/auth`) that verifies credentials.
- **External_Credential**: The password configured for Bellud (`BELLUCODE_PASSWORD`, or `OPENCODE_PASSWORD` as fallback), or a session token derived from it.
- **Internal_Credential**: The random password generated by Bellud at start and given only to the TS_Child.
- **Session_Token**: A token of the form `<expiresUnixSec>.<base64url(HMAC)>` signed with a key derived from the External_Credential.
- **Proxy**: The Bellud component (`internal/proxy`) that forwards TS-owned requests to the TS_Child.
- **Graph_Engine**: The vendored, renamed Toise engine (`internal/bellugraph`), displayed as "Bellu Graph Engine".
- **Graph_Facade**: The Bellud-owned Go interface (`Engine`, `Ingest`, `Query`) that is the only surface of the Graph_Engine used by the rest of Bellud.
- **Batch**: One collector observation set appended to the Graph_Engine as a single atomic log append.
- **Entity_ID**: The deterministic identifier of a graph entity, computed as a hash of its kind and identity attributes.
- **Collector**: A Bellud component that produces Batches from a source (host, docker, codesec, iac, secrets).
- **Redaction_Guard**: The Bellud component (`internal/redact`) that scrubs every Batch before it reaches the Graph_Engine.
- **Redaction_Pattern**: A secret-matching pattern taken from the `redaction` section of `bellu.yaml`.
- **Sync_Tool**: The program `script/sync-bellu-graph` (Go program `cmd/sync-bellu-graph`) that vendors and renames the upstream Toise tree.
- **Rename_Map**: The ordered rule file `script/rename.map.yaml` used by the Sync_Tool.
- **Allow_List**: The files permitted to contain the name `toise`: `NOTICE`, `UPSTREAM.md` and license-attribution comments.
- **Graph_API**: The Go-owned HTTP endpoints under `/api/experimental/graph/`.
- **Graph_MCP_Endpoint**: The Go-owned endpoint `/api/experimental/graph/mcp`, protected by the Graph_MCP_Token.
- **Graph_MCP_Token**: The bearer token generated in memory at each Bellud start for the Graph_MCP_Endpoint.
- **Graph_Contract**: The TypeScript group `ExperimentalGraphGroup` in `packages/protocol` and the wire schemas in `packages/schema/src/graph.ts`.
- **Web_UI**: The static assets of `packages/app/dist` served by Bellud.
- **Compatibility_Name**: An existing opencode name kept because Bellud must interoperate with existing TypeScript code: `OPENCODE_PASSWORD`, `OPENCODE_CONFIG_CONTENT`, `OPENCODE_CONFIG_DIR`, Basic-auth username `opencode`, cookie `opencode_session[_<port>]`, HMAC context `opencode-session-v1`, `@opencode/*` imports, existing `packages/*` paths, and the TS_Child database `~/.local/share/opencode/opencode-local.db`.
- **Fixture**: A recorded request and response pair captured from the TS server, used in contract tests.
- **Migration_Stage**: One ordered step of the route migration plan in which a set of route groups changes Owner from `ts` to `go`.

## Requirements

### Requirement 1: Front Door and Route Dispatch

**User Story:** As a client user (TUI, web, desktop, SDK), I want one server origin on port 4096 that serves all routes, so that I can keep using a single address and credential while routes migrate to Go.

#### Acceptance Criteria

1. WHEN Bellud starts, THE Bellud SHALL listen on the hostname from `BELLUCODE_HOSTNAME` and the port from `BELLUCODE_PORT`, using `127.0.0.1` for an unset or empty hostname and `4096` for an unset or empty port.
2. IF `BELLUCODE_PORT` is set to a value that is not an integer from 1 to 65535, or the configured address cannot be bound, THEN THE Bellud SHALL exit with a non-zero exit code and write an error to the log indicating the invalid port or the bind failure, without starting the TS_Child.
3. WHEN a request is received, THE Router SHALL resolve its Route by looking up the request method and the cleaned path in the Route_Table, where the cleaned path is the request path after collapsing repeated slashes, resolving `.` and `..` segments, and removing any trailing slash other than the root `/`.
4. WHEN more than one Route matches a request, THE Router SHALL select the most specific match, ranking exact segments above `{param}` segments, `{param}` segments above `/*` prefixes, and a specific method above `*`.
5. WHEN a Route has Owner `go` and the request passes authentication, THE Router SHALL dispatch the request to the Go handlers.
6. WHEN a Route has Owner `ts` and the request passes authentication, THE Router SHALL dispatch the request to the Proxy.
7. IF no Route matches a request, THEN THE Router SHALL authenticate the request and dispatch it to the Proxy as the default Owner `ts`.
8. IF a request to a Route with Public set to false, or to an unmatched path, fails authentication, THEN THE Router SHALL reject the request with an unauthorized response and SHALL NOT dispatch it to the Go handlers or the Proxy.
9. WHEN a request matches a Route with Public set to true, THE Router SHALL serve the request without requiring authentication.
10. WHERE CORS origins are configured through `BELLUCODE_CORS`, THE Router SHALL add CORS headers to responses for requests whose `Origin` header exactly matches a configured origin, and SHALL NOT add CORS headers for any other origin.
11. IF the hostname is not a loopback address and no password is configured, THEN THE Bellud SHALL write one warning to the log during start and continue starting.
12. THE Router SHALL select the same Route and Owner for a given method and path regardless of the order of the Routes in the Route_Table.

### Requirement 2: Route Table Validation

**User Story:** As a maintainer, I want the route ownership table validated against the protocol, so that every operation has exactly one owner and no routes conflict.

#### Acceptance Criteria

1. THE Route_Table SHALL assign every Protocol_Operation (matched by HTTP method and path) to exactly one Route, and every Route SHALL have exactly one Owner whose value is `go` or `ts`.
2. WHEN the Route_Table is loaded, THE Route_Table SHALL reject any two Routes that have the same method and the same specificity (equal literal-segment count and equal wildcard positions) and whose patterns both match at least one common request path.
3. IF a Protocol_Operation resolves to no Route, THEN THE Route_Table validation SHALL fail, name the operation method and path, and cause Bellud to exit with a non-zero status without listening on port 4096.
4. IF two Routes overlap at equal specificity, THEN THE Route_Table validation SHALL fail, name both patterns, and cause Bellud to exit with a non-zero status without listening on port 4096.
5. IF a Route has Owner `go` and either no Go handler is registered for it or its contract test against the Fixtures fails, THEN THE Route_Table validation SHALL fail and name the Route method and pattern.
6. THE Route_Table SHALL be embedded in the Bellud binary, and Bellud SHALL read no external file to obtain Routes at runtime.
7. WHILE Migration_Stage 0 is active, THE Route_Table SHALL assign Owner `go` to every `experimental.graph.*` Protocol_Operation and to the Graph_MCP_Endpoint, and Owner `ts` to every other Protocol_Operation.
8. IF a Route_Table entry cannot be parsed, has an Owner other than `go` or `ts`, or lacks method, pattern, group, owner, public flag or stream flag, THEN THE Route_Table validation SHALL fail, identify the offending entry by its position or pattern, and cause Bellud to exit with a non-zero status without listening on port 4096.

### Requirement 3: Authentication Parity

**User Story:** As a client user, I want Bellud to accept the same credentials as the existing server, so that existing clients and saved sessions keep working.

#### Acceptance Criteria

1. THE Authenticator SHALL read the External_Credential from `BELLUCODE_PASSWORD`.
2. WHERE `BELLUCODE_PASSWORD` is unset, THE Authenticator SHALL read the External_Credential from `OPENCODE_PASSWORD` (Compatibility_Name).
3. WHEN a request to a non-public route carries Basic authentication with username `opencode` (Compatibility_Name) and the External_Credential as password, THE Authenticator SHALL authorize the request.
4. WHEN a request to a non-public route carries Basic authentication with username `opencode` and a valid Session_Token as password, THE Authenticator SHALL authorize the request.
5. IF a request carries Basic authentication with a username other than `opencode`, THEN THE Authenticator SHALL reject the request, even when the password is the External_Credential or a valid Session_Token.
6. WHEN a request to a non-public route carries the cookie named `opencode_session_<port>` (Compatibility_Name), where `<port>` is the port in the Host header, or `opencode_session` when the Host header has no port, with a valid Session_Token, THE Authenticator SHALL authorize the request.
7. WHEN Bellud issues a Session_Token, THE Authenticator SHALL produce `<expiresUnixSec>.<base64url(HMAC-SHA256(key, expiresUnixSec))>`, where `expiresUnixSec` is the current Unix time in whole seconds plus 2,592,000 (30 days), `key` is `HMAC-SHA256(External_Credential, "opencode-session-v1")` (Compatibility_Name), and the base64url encoding has no padding.
8. THE Authenticator SHALL treat a Session_Token as valid only when it has exactly two dot-separated parts, the first part is an integer within the safe integer range, `expiresUnixSec * 1000` is greater than the current time in milliseconds, and the second part equals the HMAC computed for the current External_Credential.
9. THE Authenticator SHALL produce the same verification result as the TypeScript implementation in `packages/server/src/auth.ts` for every Session_Token, password, username and time in the shared fixture set, including tokens expiring at the current second, one second earlier and one second later.
10. WHEN the External_Credential is changed, THE Authenticator SHALL reject every Session_Token issued for the previous External_Credential.
11. THE Authenticator SHALL compare credentials and signatures in constant time.
12. IF the External_Credential is unset or empty, THEN THE Authenticator SHALL reject every request on non-public routes, including requests that carry an empty password or an empty Session_Token.
13. IF a non-public request has missing or invalid credentials, THEN THE Bellud SHALL respond with status 401 and a `WWW-Authenticate: Basic` header, and SHALL NOT forward the request to the TS_Child.
14. IF a request carries a malformed Authorization header (not `Basic <base64>`, invalid base64, or no `:` separator in the decoded value) or a malformed Session_Token (wrong part count, non-numeric expiry, or signature of any other length than the expected one), THEN THE Authenticator SHALL reject the request with the same response as criterion 13 and Bellud SHALL continue serving subsequent requests.

### Requirement 4: TS Child Supervision

**User Story:** As an operator, I want Bellud to run and restart the TypeScript server as a managed child, so that unmigrated routes keep working without manual process management.

#### Acceptance Criteria

1. WHEN Bellud starts, THE Supervisor SHALL spawn the TS_Child bound to `127.0.0.1` on a randomly assigned free port, so that the TS_Child accepts no connection from a non-loopback address.
2. THE Supervisor SHALL pass the Internal_Credential to the TS_Child only through the child environment variable `OPENCODE_PASSWORD` (Compatibility_Name), and SHALL NOT pass it through command-line arguments.
3. THE Supervisor SHALL keep a stdin pipe to the TS_Child open as an ownership lease from spawn until the TS_Child exits or the Supervisor closes the pipe during shutdown.
4. WHEN the TS_Child prints its `{"url": ...}` stdout line, THE Supervisor SHALL probe `/api/server/info` with the Internal_Credential and SHALL mark the TS_Child ready only after the probe returns a success response.
5. IF the TS_Child is not ready within the start timeout of 30 seconds after spawn, THEN THE Supervisor SHALL kill the TS_Child, count the attempt as a failed start, and retry using the backoff of criterion 6.
6. IF the TS_Child exits unexpectedly, THEN THE Supervisor SHALL restart it with exponential backoff starting at 500 ms, doubling after each consecutive failure, and capped at 15 seconds.
7. WHEN a restart succeeds and the TS_Child is marked ready, THE Supervisor SHALL reset the backoff delay to 500 ms.
8. WHILE the TS_Child is starting or restarting, THE Proxy SHALL respond to each TS-owned request with status 503, a `Retry-After: 2` header and a JSON error body in the protocol error shape.
9. WHILE the TS_Child is starting, restarting or degraded, THE Bellud SHALL continue to serve Go-owned routes.
10. IF the TS_Child fails to start 5 consecutive times within a 120-second failure window, THEN THE Bellud SHALL keep serving Go-owned routes, write the last 50 stderr lines of the child to the log, and report the state `degraded` in the graph status endpoint, while the Supervisor keeps retrying at the 15-second backoff cap.
11. WHEN a start succeeds while the state is `degraded`, THE Bellud SHALL clear the `degraded` state and report the child as ready in the graph status endpoint.
12. WHEN Bellud receives SIGTERM, THE Supervisor SHALL close the stdin lease, wait up to a grace period of 10 seconds for the TS_Child to exit, and then kill the TS_Child if it is still running.
13. THE Supervisor SHALL NOT write the Internal_Credential or the External_Credential to logs, including child stderr lines copied under criterion 10.

### Requirement 5: Reverse Proxy for HTTP

**User Story:** As a client user, I want proxied responses to be identical to what the TS server sends, so that migrating routes causes no behavior change.

#### Acceptance Criteria

1. WHEN the Proxy forwards a request to the TS_Child, THE Proxy SHALL deliver the same method, path, query string, end-to-end headers and body bytes as the client sent, excluding hop-by-hop headers and the External_Credential.
2. WHEN the Proxy forwards a request, THE Proxy SHALL replace the client credentials with the Internal_Credential.
3. WHEN the TS_Child responds, THE Proxy SHALL deliver the same status code, end-to-end headers and body bytes to the client, including chunked bodies split at any chunk boundary and bodies with a size of 0 bytes.
4. THE Proxy SHALL leave `Content-Encoding` and `Content-Length` headers and body bytes unmodified in both directions.
5. THE Proxy SHALL preserve the client `Host` header on forwarded requests so that the TS_Child computes the same cookie names and pairing URLs.
6. WHEN the Proxy forwards a request, THE Proxy SHALL set `X-Forwarded-For` to the client address, `X-Forwarded-Host` to the client `Host` value, and `X-Forwarded-Proto` to the scheme of the client connection.
7. THE Proxy SHALL remove the hop-by-hop headers `Connection`, `Keep-Alive`, `Proxy-Authenticate`, `Proxy-Authorization`, `TE`, `Trailer`, `Transfer-Encoding`, `Upgrade` and any header named in `Connection` from forwarded requests and responses.
8. IF the TS_Child is not running, refuses the connection, or does not return response headers within 30 seconds, THEN THE Proxy SHALL respond to the client with a gateway error status, include an error body indicating that the upstream is unavailable, and not retry the request.
9. IF the client disconnects before the response completes, THEN THE Proxy SHALL cancel the request to the TS_Child within 1 second.

### Requirement 6: Streaming Through the Proxy

**User Story:** As a client user, I want SSE and WebSocket traffic to flow through Bellud in real time, so that event feeds and terminals behave as they do today.

#### Acceptance Criteria

1. WHEN the TS_Child sends an SSE chunk, THE Proxy SHALL deliver the chunk to the client within 100 ms of receiving it, before the response ends and without buffering the whole body.
2. WHERE a Route has Stream set to true or the response content type is `text/event-stream`, THE Proxy SHALL flush to the client after every write from the TS_Child.
3. WHEN a client sends a WebSocket upgrade request on a TS-owned route, THE Proxy SHALL establish the connection to the TS_Child and copy frames in both directions.
4. WHILE a WebSocket connection is open, THE Proxy SHALL deliver frames in each direction in the order sent, with byte-identical payloads and unchanged frame type (text or binary).
5. WHEN either side of a WebSocket sends a close frame, THE Proxy SHALL pass the close frame, with its status code and reason, to the other side and close both connections within 5 seconds.
6. IF the TS_Child exits during an open SSE stream, THEN THE Proxy SHALL end the client response within 5 seconds with a normal end of stream, with no truncated event and no error body, after delivering all chunks already received.
7. IF the TS_Child exits or the upstream connection fails during an open WebSocket connection, THEN THE Proxy SHALL send the client a close frame with status code 1011 and close the connection within 5 seconds.
8. IF the TS_Child cannot be reached when a WebSocket upgrade request arrives, THEN THE Proxy SHALL reject the upgrade with an error response indicating the upstream is unavailable and SHALL NOT open a client WebSocket connection.

### Requirement 7: Credential Isolation

**User Story:** As a security-conscious operator, I want the external password kept away from the TS child and its tools, so that a compromised child or tool cannot learn it.

#### Acceptance Criteria

1. WHEN the Proxy forwards a request to the TS_Child, THE Proxy SHALL remove every client `Authorization` header and every client `Cookie` header and SHALL set exactly one `Authorization` header using Basic authentication with username `opencode` and the Internal_Credential.
2. THE Supervisor SHALL exclude the External_Credential value, including the values of `BELLUCODE_PASSWORD` and `OPENCODE_PASSWORD` as inherited by Bellud, from the TS_Child environment, command-line arguments and log output.
3. WHEN Bellud starts, THE Bellud SHALL generate a new Internal_Credential of at least 32 bytes (256 bits) from a cryptographically secure random source, different from the Internal_Credential of every previous start.
4. THE Bellud SHALL hold the Internal_Credential only in process memory and SHALL NOT write it to disk, to Bellud log output, or to any HTTP response body or header sent to a client.
5. IF the cryptographically secure random source fails while generating the Internal_Credential, THEN THE Bellud SHALL abort startup without starting the TS_Child and without binding port 4096, and SHALL exit with a non-zero status and an error message indicating that credential generation failed.
6. WHEN the Supervisor restarts the TS_Child, THE Supervisor SHALL give the restarted TS_Child the same Internal_Credential as the process it replaces and SHALL keep the External_Credential excluded as in criterion 2.

### Requirement 8: Vendored Engine Sync and Rename

**User Story:** As a maintainer, I want a deterministic tool that vendors and renames the upstream Toise engine, so that I can take upstream updates without merge conflicts.

#### Acceptance Criteria

1. WHEN invoked with a commit argument of exactly 40 lowercase hexadecimal characters, THE Sync_Tool SHALL fetch that upstream commit, verify its checksum, and write the transformed tree to `services/bellud/internal/bellugraph`.
2. IF the commit argument is not exactly 40 lowercase hexadecimal characters, THEN THE Sync_Tool SHALL exit with a non-zero status, print an error indicating the invalid commit argument, and leave the existing vendored tree unchanged.
3. IF the fetched commit does not exist upstream or its checksum verification fails, THEN THE Sync_Tool SHALL exit with a non-zero status, print an error indicating the fetch or checksum failure, write no files to the vendored tree, and leave the existing vendored tree unchanged.
4. WHEN run twice with the same commit, Rename_Map and tool version, THE Sync_Tool SHALL produce output trees whose file lists and file contents are byte-identical.
5. THE Sync_Tool SHALL process files in ascending bytewise path order and convert CRLF line endings to LF in all text files.
6. WHEN applying the Rename_Map, THE Sync_Tool SHALL apply rules in listed order and convert the Go module path to `github.com/bellu/bellucode/services/bellud/internal/bellugraph`, the proto package `toise.v1` to `bellugraph.v1`, the `TOISE_` environment prefix to `BELLU_GRAPH_`, the `toise_` metric prefix to `bellu_graph_`, the `toise://` URI scheme to `bellugraph://`, Go identifiers to `BelluGraph` and `bellugraph`, and user-facing text to "Bellu Graph Engine".
7. WHEN the Rename_Map is applied to the Sync_Tool's own output, THE Sync_Tool SHALL produce a tree with zero byte differences from that output.
8. IF any Rename_Map rule output contains text that matches the input pattern of any rule in the Rename_Map, THEN THE Sync_Tool SHALL exit with a non-zero status before reading or writing any file in the vendored tree, and print an error identifying the offending rule.
9. THE Sync_Tool SHALL exclude `internal/demo/**` and `.git/**` from the output.
10. WHEN the Sync_Tool applies the Rename_Map, THE Sync_Tool SHALL leave zero occurrences of the case-insensitive string `toise` in the output outside the Allow_List files.
11. WHEN the renamed tree is written, THE Sync_Tool SHALL regenerate the protobuf and GraphQL outputs for the renamed package, and IF regeneration exits non-zero, THEN THE Sync_Tool SHALL treat it as a failed step under criterion 13.
12. WHEN all steps succeed, THE Sync_Tool SHALL replace the vendored directory with the staged tree using a single atomic rename, remove files that no longer exist upstream, and exit with status zero.
13. IF the Sync_Tool fails at any step, THEN THE Sync_Tool SHALL exit with a non-zero status, print an error identifying the failed step, delete the staging directory, and leave the existing vendored tree byte-identical to its state before invocation.
14. THE Sync_Tool SHALL modify only files within `services/bellud/internal/bellugraph` and its own staging directory, and SHALL leave Compatibility_Name occurrences elsewhere in the repository unchanged.
15. WHEN the Sync_Tool completes successfully, THE Sync_Tool SHALL write `UPSTREAM.md` containing the upstream repository, the full 40-character commit SHA, the license identifier and the tool version, and containing no date or time value.
16. WHEN the vendored tree is produced, THE Graph_Engine's renamed upstream tests SHALL pass, with `go build ./...`, `go vet ./...` and `go test ./...` each run from `services/bellud` exiting with status zero.

### Requirement 9: No Leftover Upstream Names

**User Story:** As a maintainer, I want no upstream product names to remain in the vendored tree, so that Bellu Graph Engine is consistently branded and runtime names match.

#### Acceptance Criteria

1. WHEN the Sync_Tool finishes processing, THE Sync_Tool SHALL scan every file and every file path in the output tree for the case-insensitive string `toise` and report each occurrence outside the Allow_List.
2. IF the scan finds the string `toise` outside the Allow_List, THEN THE Sync_Tool SHALL exit with a non-zero status, print one line per occurrence containing the file path and 1-based line number (or the path only for a match in a file name), and retain the output tree unchanged for inspection.
3. WHEN the scan finds no occurrence of `toise` outside the Allow_List, THE Sync_Tool SHALL exit with status zero.
4. THE Graph_Engine SHALL contain zero occurrences of the `TOISE_` environment variable prefix, the `toise_` metric name prefix, the `toise://` URI scheme and the `toise.v1` proto package, matched case-insensitively.
5. THE Graph_Engine SHALL expose the exact human name "Bellu Graph Engine" in the debug UI page title, the MCP server name returned in the initialize response, and the MCP instructions text returned in the initialize response.

### Requirement 10: Apache-2.0 Compliance

**User Story:** As a project owner, I want the vendored code to meet its Apache-2.0 obligations after heavy renaming, so that the project stays license-compliant.

#### Acceptance Criteria

1. WHEN the Sync_Tool vendors the upstream tree, THE Sync_Tool SHALL copy the upstream `LICENSE` file into the output so that it is byte-for-byte identical to the upstream file.
2. WHEN the Sync_Tool vendors the upstream tree, THE Sync_Tool SHALL write a `NOTICE` file that contains the upstream project name and the full 40-character synced commit SHA.
3. WHEN the Sync_Tool transforms a `.go` source file that does not contain the modification notice, THE Sync_Tool SHALL insert the modification notice exactly once, after the upstream license header and before the `package` clause.
4. WHEN the Sync_Tool runs on a `.go` file that already contains the modification notice, THE Sync_Tool SHALL leave the file's notice text and position unchanged, so that a second run over the same input produces output identical to the first run.
5. WHEN the Sync_Tool transforms a file, THE Sync_Tool SHALL retain every upstream copyright, patent, trademark and attribution notice line present in that file, without alteration of its text.
6. IF the upstream `LICENSE` file is missing or the synced commit SHA cannot be determined, THEN THE Sync_Tool SHALL exit with a non-zero status, report the missing item, and leave the existing output tree unchanged.

### Requirement 11: In-Process Graph Engine and Facade

**User Story:** As a collector author, I want the graph engine to run inside Bellud behind a small Go interface, so that I can write observations without a network hop and upstream changes affect only one adapter.

#### Acceptance Criteria

1. WHERE `BELLU_GRAPH_ENABLED` is true, THE Bellud SHALL run the Graph_Engine inside the Bellud process and SHALL NOT start a separate process or open a network connection to write a Batch.
2. THE Graph_Facade SHALL expose exactly the members `Ingest`, `Query`, `MCPHandler` and `Close`, and no package of Bellud outside `internal/bellugraph` SHALL import a Graph_Engine package other than the Graph_Facade.
3. WHEN a Collector calls `Ingest().Apply` with a Batch, THE Graph_Engine SHALL append the Batch as a single atomic log append, such that after success or failure either all or none of the Batch's entities and relations are visible to `Query`, and SHALL return a receipt identifying the appended Batch.
4. IF the append of a Batch fails, THEN THE Graph_Engine SHALL return an error to the Collector, SHALL leave the graph unchanged, and SHALL keep accepting subsequent Batches.
5. THE Graph_Facade `Query` SHALL support the operations entity lookup, find, neighbors, history, changes and diff.
6. IF `Query` is called with an Entity_ID that does not exist, THEN THE Graph_Facade SHALL return a not-found error and SHALL NOT return an empty entity.
7. THE Graph_Engine MCP handler SHALL expose exactly the tools `describe_schema`, `describe_type`, `find_entities`, `get_entity`, `annotate_entity`, `get_neighbors`, `find_path`, `impact_of`, `entity_history`, `recent_changes`, `graph_diff` and `telemetry_keys`.
8. WHEN Bellud receives SIGTERM or SIGINT, THE Bellud SHALL stop accepting new requests, wait up to 30 seconds for in-flight requests to complete, then flush and close the Graph_Engine store, and SHALL exit with status 0 if the close succeeds.
9. IF in-flight requests remain after 30 seconds or the store close fails, THEN THE Bellud SHALL cancel the remaining requests, log the failure, and exit with a non-zero status without leaving a partially written log record.
10. WHERE `BELLU_GRAPH_ENABLED` is false, THE Bellud SHALL start without opening the Graph_Engine store, SHALL NOT start any Collector writes, and SHALL return a service-unavailable error indicating the graph is disabled for each Graph_API request.
11. THE Graph_Engine SHALL read its configuration from `BELLU_GRAPH_ENABLED`, `BELLU_GRAPH_DIR`, `BELLU_GRAPH_OTLP_LISTEN`, `BELLU_GRAPH_RETENTION` and `BELLU_GRAPH_LOG_LEVEL`.
12. IF any of the variables in criterion 11 holds a value that cannot be parsed (a non-boolean `BELLU_GRAPH_ENABLED`, a non-duration `BELLU_GRAPH_RETENTION`, a `BELLU_GRAPH_OTLP_LISTEN` that is not `host:port`, or a `BELLU_GRAPH_LOG_LEVEL` outside `debug`, `info`, `warn`, `error`), THEN THE Bellud SHALL refuse to start, exit with a non-zero status, and report an error naming the variable.
13. WHILE `BELLU_GRAPH_OTLP_LISTEN` is empty, THE Graph_Engine SHALL keep the OTLP listener disabled and SHALL NOT bind any OTLP port.
14. IF a Batch contains a relation that carries one or more attributes, THEN THE Bellud SHALL reject the whole Batch with a validation error identifying the offending relation, and SHALL NOT append any part of it.

### Requirement 12: Graph Storage Security

**User Story:** As an operator, I want graph data protected on disk and failures contained, so that a storage problem does not take down the whole server and data stays private.

#### Acceptance Criteria

1. WHERE the environment variable `BELLU_GRAPH_DIR` is set to a non-empty value, THE Graph_Engine SHALL store data in the directory named by that value; otherwise THE Graph_Engine SHALL store data in `~/.local/share/bellucode/graph`.
2. WHEN THE Graph_Engine opens the store and the data directory does not exist, THE Graph_Engine SHALL create the directory with mode 0700 and SHALL create every file in it with mode 0600.
3. IF the data directory has any group or world permission bit set (mode & 0077 is not 0), THEN THE Graph_Engine SHALL refuse to open the store and SHALL NOT change the directory or file permissions.
4. IF the store is locked, has wrong permissions, or is corrupt at start, THEN THE Bellud SHALL complete startup within 5 seconds with the Graph_Engine disabled, SHALL keep serving all non-graph routes, and every request to a Graph_API route SHALL receive status 503 with code `graph_unavailable`.
5. IF the store is corrupt, THEN THE Graph_Engine SHALL leave the existing log byte-for-byte unchanged and SHALL NOT create, truncate or replace any log file in the data directory.
6. IF the store lock is held by another process, THEN THE Bellud SHALL write one log entry at error level that contains the lock holder's path and SHALL start with the Graph_Engine disabled as in criterion 4.
7. THE Graph_Engine debug UI SHALL be disabled by default.
8. WHERE the Graph_Engine debug UI is enabled, THE Graph_Engine SHALL return only derived graph data (entities, edges and counts) and SHALL NOT return raw log bytes or raw log records in any response.

### Requirement 13: Graph Identity and Temporal Queries

**User Story:** As an agent or analyst, I want stable entity identities and accurate historical state, so that I can trust diffs, history and as-of queries.

#### Acceptance Criteria

1. THE Graph_Facade SHALL compute the Entity_ID as a hash of the entity kind and its registered identity attributes.
2. THE Entity_ID computation SHALL produce the same Entity_ID for the same kind and identity attribute values regardless of attribute map ordering, process, restart, or operating system and CPU architecture.
3. WHEN two entities have different kinds or different identity attribute values, THE Graph_Facade SHALL assign different Entity_IDs.
4. WHEN attributes that are not identity attributes are added, removed or changed on an entity, THE Graph_Facade SHALL return the same Entity_ID.
5. IF an entity has a kind with no registered identity attributes, or lacks a value for a registered identity attribute, THEN THE Graph_Facade SHALL reject the entity with an error indicating the missing identity attribute and SHALL leave the Graph_Engine unchanged.
6. WHEN `Query.Entity` is called with a time T, THE Graph_Engine SHALL return the state obtained by folding, in log order, all events with `observed_at` less than or equal to T, including events with `observed_at` equal to T.
7. WHEN `Query.Entity` is called with a time T earlier than the first event for the entity, or for an Entity_ID that has no events, THE Graph_Engine SHALL return a not-found result and no state.
8. WHEN `Query.Entity` is called with a time later than the last event, THE Graph_Engine SHALL return the current state.
9. THE Graph_Engine SHALL return a byte-identical `Query.Entity` result whether snapshots or caches are enabled or disabled.
10. WHEN a Batch is appended, THE Graph_Engine SHALL assign `recorded_at` at append time and SHALL preserve `observed_at` exactly as supplied by the Collector.
11. WHEN a Collector reports a full current observation, THE Graph_Engine SHALL derive added changes for entities absent from the projection, changed changes for entities whose attributes differ, and removed changes for projected entities of the same Collector scope that are absent from the observation.
12. WHEN a paginated query is made, THE Graph_Facade SHALL return at most 100 items if no page size is supplied, and at most 1000 items per page regardless of the page size requested.
13. IF a paginated query requests a page size less than 1 or greater than 1000, THEN THE Graph_Facade SHALL reject the query with an error indicating the allowed page size range of 1 to 1000.

### Requirement 14: Collectors

**User Story:** As a security analyst, I want collectors that observe the host, containers, code and infrastructure, so that the graph reflects the real environment.

#### Acceptance Criteria

1. WHEN the host Collector ticks on Linux, THE host Collector SHALL read `/proc` processes, `/proc/net/tcp*`, `/proc/net/udp*` and the hostname and produce `host`, `process` and `listening_port` entities.
2. WHEN the docker Collector ticks and the Docker socket is present, THE docker Collector SHALL use the Docker socket through a read-only API subset (list and inspect operations only, no create, start, stop, exec or delete) and produce `container`, `image`, `network` and `volume` entities.
3. WHEN the docker Collector produces a `container` entity, THE docker Collector SHALL retain only the keys of the container environment variables and SHALL drop their values, so that no environment variable value appears in the Batch.
4. WHEN the codesec Collector scans a repository, THE codesec Collector SHALL read `package.json`, `bun.lock`, `go.mod`, `requirements.txt` and `.github/workflows/*.yml` and produce `repository`, `dependency`, `workflow` and `secret_ref` entities.
5. WHEN the iac Collector ticks, THE iac Collector SHALL read Terraform `*.tf` files and Kubernetes manifests and produce `iac_resource` and `k8s_object` entities.
6. WHEN the secrets Collector ticks, THE secrets Collector SHALL scan files with a rule set and produce `secret_finding` entities containing only path, line, rule identifier and a hash prefix of 8 hexadecimal characters, and no matched secret text.
7. THE Collectors SHALL model qualifiers as entity attributes or intermediate entities and SHALL emit relations without attributes.
8. THE host Collector SHALL run at an interval of at least 5 seconds and the docker Collector at an interval of at least 30 seconds.
9. WHEN a watched file changes, THE codesec Collector SHALL start a scan within 5 seconds of the change, SHALL skip files larger than 1 MiB, and SHALL skip paths under `node_modules` and `.git`.
10. WHILE running on a platform other than Linux, THE host Collector SHALL produce no observations and SHALL not report a failure.
11. IF a Collector fails or exceeds a 30 second tick timeout, THEN THE Bellud SHALL log the failure at most once per backoff window, record the failure in the `status` attribute of a `collector_status` entity, discard the partial Batch of that tick, and continue running the other Collectors.
12. IF the Docker socket is absent, THEN THE docker Collector SHALL produce no observations, SHALL record no failure and SHALL write no error log entry.
13. WHEN a Collector tick completes, THE Bellud SHALL pass the Batch through the Redaction_Guard before calling `Ingest().Apply`.
14. IF the Redaction_Guard fails to process a Batch, THEN THE Bellud SHALL discard that Batch without calling `Ingest().Apply`, record the failure in the `collector_status` entity of the source Collector, and continue running the Collectors.

### Requirement 15: Redaction Guard

**User Story:** As a security owner, I want secret values never to enter the graph, so that graph data and agents cannot leak credentials.

#### Acceptance Criteria

1. THE Redaction_Guard SHALL compile the Redaction_Patterns into `internal/redact/patterns.go` at generation time so that Bellud has no runtime dependency on the `bellu-ai-cyber` repository.
2. WHEN a Batch is scrubbed, THE Redaction_Guard SHALL replace every substring of every string value in the Batch that matches a Redaction_Pattern with `[REDACTED:<rule_id>]`, where `<rule_id>` is the identifier of the first matching Redaction_Pattern in `bellu.yaml` order.
3. WHEN a Batch is scrubbed, THE Redaction_Guard SHALL return a Batch with the same entity IDs, the same number of entities and the same field names as its input.
4. WHEN a Batch is scrubbed, THE Redaction_Guard SHALL leave the input Batch unmodified, so that a deep comparison of the input before and after scrubbing reports no difference.
5. WHEN an already scrubbed Batch is scrubbed again, THE Redaction_Guard SHALL return a Batch deeply equal to its input.
6. WHEN the secrets Collector reports a finding, THE Collector SHALL store `hash_prefix` as the first 8 lowercase hexadecimal characters of the SHA-256 of the value and SHALL discard the value, so that the value is absent from the Batch passed to the Redaction_Guard.
7. IF a string in a scrubbed Batch still matches a Redaction_Pattern, THEN THE Bellud SHALL drop the whole Batch without appending any part of it to the Graph_Engine, return `ErrSecretLeak` to the calling Collector, and emit one audit event containing only the Collector name and the rule identifier.
8. THE Graph_Engine SHALL store no event containing a secret matched by a Redaction_Pattern or any substring of that secret longer than 8 characters.
9. IF a Redaction_Pattern fails to compile at generation time, THEN THE Redaction_Guard generation SHALL fail with an error naming the rule identifier and SHALL leave the previous `internal/redact/patterns.go` unchanged.

### Requirement 16: Experimental Graph HTTP API

**User Story:** As a client developer, I want a typed graph query API, so that UIs and tools can read the graph through the existing client.

#### Acceptance Criteria

1. THE Graph_API SHALL provide the following `GET` endpoints under `/api/experimental/graph`: `/entities`, `/entities/:id`, `/entities/:id/neighbors`, `/entities/:id/history`, `/changes`, `/diff`, `/schema` and `/status`.
2. THE Graph_API SHALL be implemented in Go with Owner `go` in the Route_Table and SHALL not be implemented by the TS_Child.
3. THE Graph_API SHALL return response bodies that conform to the wire schemas of the Graph_Contract.
4. IF a request to the Graph_API carries no credential, or a credential that is neither the External_Credential nor a valid Session_Token, THEN THE Graph_API SHALL respond with status 401 and SHALL not execute the query.
5. IF a request to `/entities/:id`, `/entities/:id/neighbors` or `/entities/:id/history` names an Entity_ID that does not exist in the Graph_Engine, THEN THE Graph_API SHALL respond with status 404 and an error body indicating the entity was not found.
6. IF a request to the Graph_API has a malformed parameter (an Entity_ID that is not a valid Entity_ID, a non-integer or negative page limit, or an unparseable `/diff` or `/changes` range), THEN THE Graph_API SHALL respond with status 400 and an error body naming the offending parameter.
7. WHEN a graph query specifies a page limit above the hard maximum of 1000, THE Graph_API SHALL apply a limit of 1000 and SHALL return the applied limit in the response.
8. WHEN a graph query omits the page limit, THE Graph_API SHALL apply a default page limit of 100.
9. WHEN the status endpoint is called, THE Graph_API SHALL report the Graph_Engine state and the TS_Child state, and SHALL respond with status 200 within 1 second even if the TS_Child is not running.
10. THE Graph_MCP_Endpoint SHALL accept only the Graph_MCP_Token as `Authorization: Bearer` and SHALL respond with status 401 for any other credential, including the External_Credential, a Session_Token and a missing header.
11. THE Bellud SHALL generate the Graph_MCP_Token at each start from a cryptographically secure source with at least 256 bits of entropy, keep it in memory only, and compare it in constant time.
12. THE Graph_MCP_Token SHALL grant access to the Graph_MCP_Endpoint only, and a request using it on any other Bellud route SHALL be rejected with status 401.
13. WHEN `annotate_entity` is called through the Graph_MCP_Endpoint, THE Graph_Engine SHALL write an audit record containing the token identity, the target Entity_ID and the timestamp before returning success.
14. IF writing the audit record for `annotate_entity` fails, THEN THE Graph_Engine SHALL not apply the annotation and THE Graph_MCP_Endpoint SHALL return an error response indicating the audit failure.

### Requirement 20: Web UI Serving

THE Web_UI SHALL send `X-Content-Type-Options: nosniff` on every response it serves with status 200, and a Content-Security-Policy whose `script-src` includes `'sha256-<digest>'`, where the digest is the base64 SHA-256 of the content of the inline script with id `oc-theme-preload-script` when serving `index.html`.

### Requirement 21: OpenAPI Merge

**User Story:** As an SDK consumer, I want one `/openapi.json` that describes every route Bellud serves, so that tooling sees a complete contract.

#### Acceptance Criteria

3. WHEN the merged document is produced, THE Bellud SHALL remove every operation whose Route_Table Owner is `go` but which the TS_Child document still declares, so that each method and path pair appears exactly once and carries the definition from the embedded Go contract document.
4. WHEN the merged document is produced, THE Bellud SHALL cache it, and WHEN the TS_Child restarts, THE Bellud SHALL discard the cached document and repeat the fetch and merge once the TS_Child is ready again.
5. IF a fetch attempt fails by timeout, connection error, non-success response, or a body that is not a valid OpenAPI document, THEN THE Bellud SHALL retry up to 3 more times at 1-second intervals, and IF all attempts fail, THEN THE Bellud SHALL serve a document containing only the Go-owned operations, SHALL NOT cache it, and SHALL repeat the fetch on the next `/openapi.json` request.
6. WHEN a client requests `/openapi.json`, THE Bellud SHALL respond with the cached merged document within 100 milliseconds.

### Requirement 22: Staged Migration and Contract Compatibility

**User Story:** As a maintainer, I want each route group to move to Go only when it is provably compatible, so that clients see no regression.

#### Acceptance Criteria

3. WHEN the contract tests replay a Fixture against the Go handler, THE contract tests SHALL verify that the status code equals the Fixture status code, the content type equals the Fixture content type, and the response body is valid against the protocol schema for that operation.
4. WHERE an operation streams SSE, THE contract tests SHALL verify that each emitted event payload is valid against the event schemas and that the event type sequence equals the Fixture event type sequence.
5. WHEN an operation changes Owner from `ts` to `go`, THE Bellud SHALL return, for every recorded Fixture of that operation, the same status code as the Fixture and a body valid against the protocol schema.
6. THE Bellud SHALL follow the migration order: Stage 0 proxy front door and graph routes; Stage 1 auth, pairing and Web_UI; Stage 2 server info, health and event feed; Stage 3 and later the remaining groups ordered by data dependency, with the LLM session runtime last.
7. WHILE a Go-owned group needs session data held by the TS_Child, THE Bellud SHALL read it through the TS_Child HTTP API with the Internal_Credential.
8. THE Bellud SHALL never open the TS_Child SQLite database `opencode-local.db` (Compatibility_Name).
9. THE contract test job SHALL run the same Fixture set against the TS server and against Go for every Go-owned operation and SHALL fail if either run has one or more failing Fixtures.
10. THE Proxy SHALL add a median latency of under 1 ms, measured over at least 1,000 requests with a body of at most 4 KiB, and a benchmark result of 1 ms or more SHALL block promotion of that Migration_Stage.
